# M4.3 working-state benchmark

Status: harness implemented and smoke matrix recorded; statistically useful
reference run pending. Updated 2026-09-13.

## Question and controls

The benchmark compares the unchanged native-Git SQL publication path with the
opt-in fsynced journal. Both modes begin from the same committed fixture, execute
the same SQL transaction boundaries, mutate verified existing keys, and retain
required durability calls. Journal runs assert that `refs/repodb/data` does not
advance. Checkpoint timing is reported separately so moving work off the save path
does not make the total cost disappear.

Run:

```sh
make m4.3-bench
```

The durable-save matrix covers 1,000, 10,000, and 50,000 rows; batches of 1, 10,
and 100 exact-key updates; both persistence modes; 30 operations per sample; and
five independent samples with allocations. It reports journal bytes appended per
operation and phase counters for state loading, tree mutation, reachability,
object preparation, encoding, append, and flush. The checkpoint control exports
batches of 1, 10, and 100 changes. A separate growth benchmark compares fresh
full replay with cached access after 1, 10, and 100 journal generations.

Record the exact revision, `go version`, `git version`, OS, CPU, filesystem and
mount durability settings, power state, and raw `go test` output with each
published run. The benchmark records every timed transaction and reports p50,
p95, and maximum individual request latency from those observations. Go benchmark
`-count` produces independent distributions of sample averages; it does not turn
those averages into an application-request p95. Use enough `-benchtime=Nx`
transactions within every sample to measure tails, and use `-count` separately to
check run-to-run stability.

## Acceptance interpretation

Approximately 10 ms for a durable small save and 50 ms for a complete warm board
request are product targets on the declared reference machine, not guarantees.
The current harness measures the save target only. It does not yet implement the
realistic 1,000 issue / 100 author / 10,000 comment / 50,000 event fixture, board
queries, persistent MySQL-client timing, process contention, journal growth,
compaction stalls, full sync, or live/peak RSS. Those omissions are explicit
milestone gaps and prevent an adopt decision.

## Incremental replay and phase attribution

The next narrow pass added verified-offset caching, safe replacement/truncation
detection, per-request tails, and phase counters. These are one 30-request sample
per size for one-row updates, so they are diagnostic rather than final reference
percentiles:

| Rows | Mean | p50 | p95 | Max | Prior state | Snapshot build | Flush |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1,000 | 7.15 ms | 6.35 ms | 7.94 ms | 28.72 ms | 0.73 ms | 1.16 ms | 4.59 ms |
| 10,000 | 16.63 ms | 16.15 ms | 23.23 ms | 52.32 ms | 0.86 ms | 8.32 ms | 5.74 ms |
| 50,000 | 16.68 ms | 16.35 ms | 23.09 ms | 81.85 ms | 0.76 ms | 8.73 ms | 6.63 ms |

`Snapshot build` now contains tree mutation but no exact reachability walk in
journal mode. The journal conservatively retains prior immutable objects and
defers pruning to checkpoint/compaction. Remaining mean phases were:

| Rows | Tree mutation | Object copy | Encode | Append | Journal bytes | New object bytes |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1,000 | 1.14 ms | 0.08 ms | 0.11 ms | 0.06 ms | 132 KB | 91 KB |
| 10,000 | 8.24 ms | 0.29 ms | 0.53 ms | 0.14 ms | 428 KB | 294 KB |
| 50,000 | 8.58 ms | 0.43 ms | 0.53 ms | 0.14 ms | 2,021 KB | 1,479 KB |

Before reachability was deferred, its mean cost was 0.66 / 6.33 / 31.00 ms at
1k / 10k / 50k rows. At 10 generations, fresh full replay took 39.3 ms while a
verified cached read took 45 microseconds; at 100 generations those figures were
116.3 ms and 49 microseconds. Cached ordinary saves read zero prior journal bytes;
tests separately verify that another engine's appended frames are replayed from
the cached offset and that file replacement forces full validation.

A separate five-request diagnostic forced every save to be the first clean-to-
dirty transaction after a checkpoint. Its p50 was 17.95 / 20.34 / 22.37 ms at
1k / 10k / 50k rows, versus the lower dirty-journal steady-state figures above.
The current correctness path checks the Git head at both transaction start and
publication while clean. These five observations are not a useful p95, but they
make the clean transition cost visible instead of hiding it in a 30-request tail.

This isolates the current floor: the 1k-row p95 reaches the provisional 10 ms
target, but 10k/50k saves remain around 16 ms mean because Prolly mutation and
`fsync` dominate. The remaining encoded object payload can still reach roughly
2 MB. That is sufficient evidence to prototype typed row/schema edit records with
a read overlay and defer canonical Prolly materialization to checkpoint, while
continuing to report the displaced checkpoint cost.

## Typed-edit lower bound

`BenchmarkM43TypedEditJournal` is the resulting benchmark-only experiment. It
uses RepoDB's typed primary-key and row encodings, a framed/checksummed record
with fields for row and schema changes, one `fsync` per transaction, and publishes
the in-memory read overlay only after the flush. It is intentionally not an engine
persistence mode and excludes SQL parsing, cross-process locking, recovery, and
schema-change execution. Thirty individual transactions produced:

| Row edits | Mean | p50 | p95 | Max | Bytes/save | Flush |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 4.67 ms | 4.48 ms | 6.39 ms | 6.82 ms | 179 B | 4.64 ms |
| 10 | 4.45 ms | 4.37 ms | 5.37 ms | 5.37 ms | 1,304 B | 4.41 ms |
| 100 | 4.91 ms | 5.06 ms | 5.36 ms | 5.42 ms | 12,910 B | 4.75 ms |

The paired in-memory canonical checkpoint experiment applied 100 accumulated
typed edits and walked the resulting Prolly graph in 1.17 / 8.29 / 26.26 ms for
1k / 10k / 50k base rows. It deliberately excludes Git object hardening and ref
publication, which remain visible in the existing checkpoint benchmark.

```sh
go test ./engine -run '^$' \
  -bench '^BenchmarkM43TypedEdit(Journal|Checkpoint)$' \
  -benchmem -benchtime=30x -count=1
```

This establishes a plausible sub-10-ms persistence floor on the test machine and
removes catalog size from journal bytes. It justifies a real typed-edit journal
prototype with overlay recovery and checkpoint materialization; it does not by
itself establish end-to-end SQL latency or durability correctness.

No reference percentiles are claimed until the reproducible multi-sample matrix
is run and its raw output is checked in. The implementation decision is therefore
**revise**: retain
the prototype and native-Git control, complete durability/concurrency hardening and
the missing realistic/recovery measurements, then reconsider the default. See
[working-state.md](working-state.md) for the protocol and assigned rollout work.
